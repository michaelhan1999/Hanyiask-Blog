过去一年多，我参与了好几个 LLM 应用的产品化项目。从智能客服到文档问答，从代码辅助到内容生成，每做一个项目就对 LLM 应用的产品化多一层理解。

这篇文章把我的思考系统整理一下，不一定对，但希望对正在做类似探索的人有一点参考价值。

## LLM 应用的第一性原理

在讨论具体产品形态之前，需要先想清楚一件事：**LLM 应用和传统软件产品的本质区别在哪里？**

传统软件是确定性的——输入 A，经过确定的逻辑，输出 B。如果输出不对，是代码有 bug，修 bug 就好了。

LLM 应用是概率性的——输入 A，模型输出 B，这次和下次不一样。模型可能今天回答正确，明天因为 context 长度变化就回答错了。这种不确定性是模型固有的，不是 bug，不能通过修代码解决。

理解了这个区别，就理解了很多 LLM 产品失败的根本原因：产品经理在用设计确定性产品的方式设计不确定性产品。

## 什么时候该用 LLM

我有一个简单的决策框架：**当用户愿意为"大概正确"付费时，用 LLM；当用户需要"绝对正确"时，慎用。**

这个框架可以帮助快速排除很多不适合 LLM 的场景。

比如"帮我写一封商务邮件"——用户需要的是"好用的模板"，LLM 写出来的"大概能用"就够了，这个场景适合用 LLM。

比如"帮我算一下这个财务数据是否准确"——用户需要的是精确结果，任何错误都可能导致严重后果，这个场景不适合直接用 LLM，至少不能不加校验地直接用。

## Prompt Engineering 被严重低估了

在整个 LLM 应用开发流程里，Prompt Engineering 是被严重低估的环节。

很多人以为 Prompt 就是写几句话的事情。实际上，在真实产品中，Prompt 往往是一套复杂的指令体系：System Prompt 定义角色和边界 Few-shot Examples 提供参考案例，Output Format Specification 定义输出格式，Constraint Rules 定义各种约束条件……

好的 Prompt 设计可以让模型表现提升 20-30 个百分点，效果可能比换一个大参数模型还明显。但 Prompt 优化又是一个极其依赖领域知识和产品感觉的工作，这恰恰是 AI PM 可以深度参与的环节。

## 幻觉问题怎么解决

被问到最多的技术问题：LLM 胡说八道怎么办？

答案很残酷：**LLM 本身无法保证不胡说。这是模型的固有问题，不是在应用层可以完全解决的。**

但产品层可以有缓解手段：

**RAG（检索增强生成）** 是目前最有效的方案——让模型在回答之前先检索相关文档，然后把检索结果作为 context 一起给模型。模型不是在自己知识库里搜索，而是被强制"限定"在已知信息范围内。

这个方案的问题是需要维护一个检索系统，增加了工程复杂度。什么时候值得做 RAG？我的经验是：当回答准确性的重要性 > 响应速度 + 工程成本时，做。

## 成本结构是产品决策的一部分

LLM 应用有一个传统软件没有的成本维度：**token 消耗 = 钱。**

每一次 API 调用都是成本。这个成本结构直接影响了产品设计：上下文越长成本越高，流式输出比非流式用户体验好但工程更复杂，模型越大效果越好但成本也更高。

做 AI 产品经理，必须对成本有清晰的概念。不需要会优化模型，但需要知道：什么样的产品设计会产生什么样的 token 消耗量级，用户愿意付的钱能不能覆盖成本。

这个问题在 ToB 产品里尤其重要。很多 ToB AI 产品失败，不是因为效果不好，而是因为成本结构算不过来账。

## 写在最后

LLM 应用的产品化和传统软件产品化，底层逻辑是一样的：用户愿意付费的是解决问题的价值，不是技术本身。

但因为 LLM 的不确定性特征，产品设计需要在更早的阶段就把"AI 能做什么、不能做什么"纳入约束条件。这对 AI PM 提出了更高的要求：既要有传统 PM 的用户洞察和商业思维，又要对 LLM 能力边界有足够深的体感。

这条路没有捷径，只有在实战中不断积累。
