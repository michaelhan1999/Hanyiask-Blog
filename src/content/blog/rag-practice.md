RAG（Retrieval-Augmented Generation，检索增强生成）是目前 LLM 应用落地最主流的架构方案。这不是秘密，但真正动手做过的人才知道工程化的过程中有多少坑要踩。

这篇文章总结我最近一年做 RAG 项目的实战经验，不讲理论，只讲踩过的坑和解决方案。

## RAG 不是什么魔法

先说清楚 RAG 能做什么、不能做什么。

RAG 的核心思想很简单：**让模型在回答之前先检索相关的文档，然后把文档作为 context 给模型。** 这样模型不是在"凭空编造"，而是在"基于已知信息回答"。

这解决了 LLM 幻觉的问题，但引入了新的问题：**检索的质量直接决定回答的质量。** 如果检索不到正确的内容，模型一样回答不出来。

所以 RAG 系统有两个核心环节：**检索（Retrieval）+ 生成（Generation）。** 两者都做好，系统才工作得好。

## 文档处理的坑

RAG 系统的第一步是文档处理。这个环节有非常多的工程细节需要注意。

**首先是切分策略。** 你需要把长文档切成小块（chunk）才能索引。但怎么切是个技术活。

最简单的是固定长度切分——比如每 500 个 token 切一块。这个方法快，但容易把语义相关的段落切成两半，导致检索不到相关内容。

好一点的是按语义切分——按照自然段落或者语义边界切。但实现起来更复杂，需要额外的 NLP 能力。

我的经验是：**先按语义段落切，如果段落太长再按固定长度拆分。** 这样能保证每个 chunk 的语义完整性。

**然后是元数据提取。** 每个 chunk 除了内容本身，还需要存储来源文档标题、章节、页码等元数据。这些信息在生成答案时可以帮助模型判断内容的可信度，也可以在用户提问时做过滤。

**最后是格式解析。** PDF、Word、网页、飞书文档——不同的文档格式需要不同的解析方案。尤其是表格和图片里的文字，解析难度很高。我目前的方案是用 marker 把 PDF 转成 markdown，再用正则提取表格内容。

## 检索优化的坑

检索是 RAG 系统里被讨论最多的环节，但也最容易过度工程化。

**向量检索 vs 关键词检索。** 很多人一上来就用向量检索（embedding similarity），但实际上 BM25 这种关键词检索在很多场景下效果更好，而且速度快得多。

我的建议是：**先用关键词检索作为 baseline，效果不够再叠加向量检索。** 两者不是替代关系，是互补关系。

**Embedding 模型的选择。** 中文场景下，bge 和 text2vec 都是不错的选择。关键是要选在跟你业务领域相关的语料上微调过的模型——通用的 embedding 模型在自己的垂直领域效果往往一般。

**Top-K 的选择。** 检索多少个 chunk 喂给 LLM？这个数字直接影响回答质量和成本。太多 context 会稀释关键信息，太少可能漏掉相关内容。我的经验是 5-10 个 chunk 是一个不错的起点。

## 生成优化的坑

检索到相关 chunk 之后，就到了生成环节。这个环节的坑主要在于 prompt 设计。

**System Prompt 怎么写。** System Prompt 需要明确告诉模型：你是谁、你应该怎么回答、你应该在什么情况下说"不知道"。我见过太多 RAG 系统的 System Prompt 写得很敷衍，导致模型要么乱编内容来源，要么回答跑偏。

一个好的 RAG System Prompt 应该包含：
- 模型的角色定义
- 回答的格式要求
- 如何引用检索到的内容
- 什么时候应该拒绝回答或说不知道

**回答的可信度问题。** 模型有时候会引用完全不相关的内容来回答问题，即使检索结果里有相关内容。这时候需要加一些约束——比如要求模型在回答时必须引用具体的文档标题和页码，这样至少有个迹可循。

## 评估：最难但最重要的事

RAG 系统的评估是最容易被忽略、但其实最重要的环节。

很多团队上线 RAG 系统后，靠人工测试几个 case 就觉得可以了。结果上线后用户反馈"AI 答非所问"。

我的建议是：**从第一天就建立评估数据集。**

评估数据集里应该包含：
- 典型问题 + 期望答案
- 模型容易出错的问题
- 边界 case

每次修改系统后，跑一遍评估数据集，看各项指标的变化。这个过程枯燥，但这是唯一能保证系统持续改进的方式。

## 写在最后

RAG 是一个听起来简单、做起来复杂的系统。它的复杂度不在于某个单点技术，而在于整个链路上的工程细节——文档解析、chunk 策略、检索算法、prompt 设计、评估体系，每个环节都有坑。

但正因为有这些坑，才是技术人的机会。如果你能在这些坑上积累足够的经验，这就是可以变现的专业能力。
